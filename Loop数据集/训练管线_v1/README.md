# Loop训练数据管线：从患者表到模型样本

本目录完成一个具体任务D01b：可执行的研究数据管线。原患者表、官方原始数据、患者划分保持不变。没有训练患者模型或RL策略，也没有接入真实给药服务。

## 1. 5分钟从哪里来

5分钟是上一版代码 `STEP=300` 的观测网格，以及旧资格清单采用的恒定基础率区间。**它不是RL-DITR论文要求的动作周期，不是“只能预测5分钟”，也不是要求患者每5分钟操作App。** 6小时前史同样是本项目的研究设置，而非原论文的固定要求。

以下三个量独立：

| 量 | 当前实现 | 含义 |
|---|---|---|
| 观测网格 | 5分钟，真实值与缺失标记保留 | 数据的记录分辨率 |
| 动作持续时间 | 5、15、30、60分钟均有独立索引 | 指定区间内保持的基础率 |
| 模型推演/规划范围 | 接口支持多步真实序列；最终范围未冻结 | 可以包含多次不同动作，不能从采样频率直接决定 |

默认5分钟只是兼容原资格清单、供患者模型学习基础转移的起点。最终产品动作持续时间在合同中是null，需通过模型多步预测和独立闭环比较后确定。长周期研究可以现在选对应索引，不必重做全部原始清洗。

长周期样本要求整个区间：每个5分钟目标均通过原资格、属于同一连续片段、基础率完全相同、剂量积分完整、后续CGM真实可用。不会将变化速率平均成一个并未执行过的恒定动作。一个30分钟动作与一条包含六次不同5分钟动作的30分钟计划是不同对象。

## 2. 如何对应两篇参考材料

- **方法论：RL-DITR，Nature Medicine 2023。** 已核对本地原文PDF第11–12页及页面图像。原任务为住院T2D、每日七个餐前/后及睡前时段，动作是注射剂量，不是T1D泵基础率。原文先训练历史表征fR、动作条件转移fT和血糖/WTR预测fP，再以患者模型为环境，结合历史动作监督和策略梯度训练策略/价值，并进行多步规划。原文使用3层Transformer、宽256、8头和MLP，而不是原文使用GRU。此前项目中的GRU是可选的自行简化方案。
- **缺失处理参考：用户提供的GlucoFM，2605.30865v2.pdf。** 上一阶段采用真实观测mask、保留NaN、长缺口断段；它不替代RL-DITR的动作条件患者模型。
- 本管线为fR提供历史与掩码，为fT提供历史动作和时长，为fP提供未来真实CGM与WTR标签；同时提供奖励和连续动作序列，供随后实现监督约束与模型式RL。历史模仿仍是对照基线，不将整个项目改成纯模仿学习或纯模型无关RL。
- F若是仅依赖历史的外部预测器，仍不能替代fT。Loop中的原动作来自原有治疗/控制系统，不能自动称为最优专家动作。历史拟合不证明更换剂量后的反事实有效性；需要独立评价。

来源：[RL-DITR正式论文](https://www.nature.com/articles/s41591-023-02552-9)、[本地论文](../../参考论文/RL-DITR_NatureMedicine_2023.pdf)。全文提取保存在文献目录供追溯，不改写原PDF。

## 3. 当前冻结的输入

默认 `core` 模式每个样本 `state.shape=(72,14)`。三个数值通道为CGM mmol/L、此前5分钟基础输注U、此前5分钟已记录Bolus U。每个通道分别附加观测标记、距最近记录的时间和该时间是否已知，再加网格时差和相对决策时点。

| 列位置（从0开始） | 内容 |
|---|---|
| 0–2 | 三个数值，按训练组观测值标准化；未知位置为占位0 |
| 3–5 | 对应的记录/观测掩码，1为有记录，0为未知 |
| 6–8 | log1p(距最近记录的小时数)，最多计24h；不是补入上次测量值 |
| 9–11 | 上述时间是否有历史依据，未知时0 |
| 12 | 网格步长，小时 |
| 13 | 当前历史格相对决策时点的小时数 |

数值0不等于缺失：真实暂停/零量有观测掩码1；缺失占位0有掩码0。原Parquet中的NaN仍保留，不向前填充、不插值。CGM使用真实观测时间计算记录年龄，其他区间量的年龄依据区间结束格；不能声称知道全部原事件的在线到达延迟。

归一化只用225名train患者合格5分钟目标所需历史行的并集，每个原网格行只统计一次。只统计有观测依据的值，不让重复切窗改变统计权重；validation、sealed_test、demo不拟合统计。长动作视图共用此冻结统计，便于统一比较。

`retrospective_multimodal` 是显式可选模式，另加碳水和运动记录及其掩码，得到72×22。碳水冲突时屏蔽；没有运动事件为未知，不是证实未运动。**这些信息的事件时间不证明录入时间，默认策略输入关闭这两个通道。** 这不是证明核心泵日志已能实时到达：整个数据源仍是回顾性数据，在线到达/修订可用性尚未验证。

患者ID、split、episode、未来CGM/剂量、资格标记、来源引用和事后问卷不进入state。IOB、性别、体重和其他静态档案本版也不直接加入；它们可供后续独立特征合同审查，不凭齐全程度缩小本版主池。

## 4. 每个样本包含什么

`LoopDataset[index]`返回：

- `state`、`next_state`：当前/下一时点的历史编码；只有state可用于当前actor。next_state用于观测到后果后的学习。
- `action_u_h`、`action_duration_minutes`、`basal_interval_u`：速率、持续时间、积分量三者绑定，不是单次注射处方。
- `target_glucose_mmol_l`、`target_wtr`：区间内每个5分钟的真实后续观测，不由插值补全。
- `reward`、`discount`：时间一致的即时研究奖励及区间折扣。
- `terminated=False`：没有证据可把资料结束视作真正临床终止。
- `truncated`：下一段同长度日志动作不再可用；`bootstrap_valid`独立表示下一真实状态是否有足够历史。不能使用`terminated or truncated`统一清零后续价值。
- `outcome_bolus_*`：区间中的已记录Bolus及记录标记，**单独的后果诊断信息，不在当前state内**。无记录的数值占位0必须与mask一起读，`actual_absence_verified`始终为false。不能在新动作的模拟分支中偷用历史后续Bolus，未来协同干预情景仍需定义。
- 患者、原主表行号、时点及片段编号：用于核验溯源。

`trajectory()`按同患者、同episode和真实时间推进，最长步数可指定。遇到缺口返回较短序列，不补造末端值。后续训练若做padding，必须使用单独的loss mask。患者模型开环推演时不能逐步把返回的未来真实state灌给自身；那些真实state只用于监督/一致性目标。

## 5. 奖励：复用论文公式，明确时间尺度改动

使用作者公开代码`glu2risk`的状态评分，公式内部的b是mg/dL，输入mmol/L先乘18：

```text
b < 70：score = -1
其他：score = 1 - clip(10 × [1.509 × (ln(b)^1.084 - 5.381)]^2, 0, 15.5) / 7.75
```

**本轮发现并解决了论文印刷公式与作者实现的括号差异。** 直接照印刷式写成`1.509×ln(b)^1.084−5.381`会使正常血糖也大量饱和到最低奖励，新增低血糖对照测试因此失败。作者[固定commit的实现](https://github.com/rlditr23/RL-DITR/blob/5080fdbe43979f9b8a9616fbc120aae4ac25842a/ts/datasets/rl.py#L5-L15)明确是`1.509×(ln(b)^1.084−5.381)`，与[风险指标研究公式](https://pmc.ncbi.nlm.nih.gov/articles/PMC4738215/)一致。现已改为作者代码的括号，加入正常血糖/低血糖及区间内恶化的回归测试；不是为了通过测试随意调整奖励。不复制作者将缺失奖励填0、片段末尾累计回报归0的处理，因为本数据的缺口边界语义不同。

本版使用下一真实CGM计算该时点的评分。长动作奖励为区间内各真实观测评分的按时间折扣求和，每个5分钟评分乘5/60小时。项目冻结 `gamma_hour=0.9`，对应Δ小时折扣 `0.9^Δ`；**这是本项目按真实时长改写的研究超参数，不能把原文每日七时段的每步0.9不加转换地用于5分钟。** 同一串观测拆成两个区间或一个长区间，折扣回报一致，已有测试验证。

WTR标签使用原文3.9–10.0 mmol/L的逐点分类范围；这里是研究标签，不是对所有患者的个体化目标。该奖励不包含临床安全约束的全部要求；不将奖励值或高WTR当作安全证明。区间内离散CGM评分之和也不是连续监测完全无缺的临床TIR。

胰岛素延迟作用由历史编码、动作条件转移和多步回报承担，不能将一次后续观测变化归因于刚才的基础率。当前数据无法保证这些机制已经可辨识。

## 6. 运行与后续训练接口

在项目根目录，本机现有数据环境可运行：

```bash
Loop数据集/预处理_v1/.venv/bin/python Loop数据集/训练管线_v1/pipeline.py smoke
Loop数据集/预处理_v1/.venv/bin/python -m unittest discover -s Loop数据集/训练管线_v1 -p 'test_*.py' -v
```

进入本目录后，训练代码可这样取一批30分钟动作样本：

```python
from pipeline import LoopDataset
dataset = LoopDataset(split='train', duration_minutes=30)
batch = next(dataset.iter_batches(batch_size=32))
# batch['state']: (32, 72, 14)
# batch['action_u_h']: (32,)
# batch['target_glucose_mmol_l']: (32, 6)
```

索引只保存患者ID和原行号，不复制海量重叠窗口。每个加载器缓存一个患者，批次遍历先打乱患者再打乱其样本，避免逐条随机读不同患者文件。返回NumPy数组，可在CUDA机器上用torch.from_numpy移入GPU。建议先用提供的患者局部批次迭代器；直接DataLoader全局shuffle可能频繁重读患者文件，影响吞吐。

sealed_test默认拒绝实例化；只有最终评价时显式传入`allow_sealed_test=True`。本轮仅对封存组执行固定结构规则和hash校验，未用其模型效果选择参数。

依赖沿用已固定的数据环境：pandas 2.2.3、numpy 2.3.5、pyarrow 25.0.1。CUDA端另需适配显卡的PyTorch，不拷贝Mac虚拟环境到Linux/Windows。

## 7. 4090是否够

**对于首版RL-DITR量级的时序患者模型和策略网络，单张24GB RTX 4090是合理且预计足够的开发/训练配置。** 数据总量主要影响训练时间与磁盘读取，不要求把全部患者或165万重叠窗口一次放入显存。官方显存依据：[NVIDIA RTX 4090](https://www.nvidia.com/en-us/geforce/graphics-cards/40-series/rtx-4090/)。

容量探针按历史/动态两个3层Transformer、宽256、8头、三个MLP头构建，约514万参数；仅FP32参数、梯度和Adam两个状态合计约82MB，此外还有激活、中间展开、CUDA工作区等，不能用82MB当训练总显存。32×72×14的FP32输入约0.123MiB；多个序列/目标也分批传入。

建议起点为batch32、历史72格、短展开12步，先测吞吐与峰值显存；参数来自容量起点，不是已证明的最佳训练配置。若训练三个患者模型集成，可以顺序训练。外部大预测器、大规模beam search、长展开和同时驻留多个模型需要另测。CPU内存32GB可作为起点，64GB更宽裕；按患者读取，避免将所有重叠窗口物化到内存。

`benchmark_cuda.py`提供CUDA上的合成前向/反向容量测试：

```bash
python benchmark_cuda.py --batch-size 32 --unroll 12 --output cuda_capacity_result.json
```

脚本不下载数据、不调用LLM，合成张量不代表真实模型训练。**本机是Mac且没有CUDA/PyTorch，脚本仅通过语法检查，尚未在4090执行；不能报告训练耗时、CUDA兼容或峰值显存实测值。** 即便容量测试通过，也只证明对应配置的容量，不证明模型有效。
